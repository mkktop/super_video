双路并行产品化时（2026-08-25），进度聚合 bug 让上报 fps 虚高约 2 倍（假 85fps），用户看
任务耗时当场拆穿（"我看总生成时间是一样的"——单路 130s vs 双路 128s）；随后又追问
"两个产物都是精确 5459 帧，你这是产了两遍吗"——那是 A/B 对照的两次独立任务，不是一次
任务重复处理。

**Why:** 从进度事件推导的 fps/帧数可能因聚合或口径 bug 虚高，而用户核对的是耗时、产物
帧数这类硬数据；虚高数字报出去会被当场对上账，损失信任。

**How to apply:** 报性能数字前先用 `elapsed_s` × 帧数反推验证与上报口径一致；做 A/B 对照
实验时主动说明多个产物是不同配置的独立任务（防"重复处理"误会），并给出证据链（帧数
精确一致、耗时符合工作量、checkpoint 段号互不重叠）。相关：[[uint8-graph-wrap-speedup]]、
[[trt-component-installer]]。

**口径跨会对账（2026-08-27 追加）**：出全模型基准表后用户立刻质疑"AnimeJaNai V3 HD L2
我记得之前 TRT 有 78 帧"——他指的是 08-25 双路并行+NVENC 的端到端 77.5fps（5459 帧
长片，单路 NVENC 42.0），而新表是纯推理 process() 单帧口径。两套数据其实自洽：TRT 推理
4.0ms@960x540→1080p（249fps 冗余）换算 1080p→4K 面积 ≈15-17ms（~60fps 上限），与当年
热缓存 e2e 49.5~51.5fps / 双路 77.5fps 吻合。教训：报任何基准前先逐项标注口径（推理-only/
e2e/分辨率），并主动和 BENCH.md 里的历史头条数字做一次换算对照——用户脑子里存着这些
旧数字，新表不像样他会当场拿出来对。
